# Design

## Context

见 `proposal.md`。当前预览把生成脚本放入只允许脚本运行的 iframe，脚本可使用受控的 `localStorage` 兼容层。提交生成请求后，键盘焦点留在工作台表单；只检查脚本语法，无法证明按钮和方向键完成了需求。内置费用示例已有录入和本地恢复逻辑，但缺少删除交互。

## Goals / Non-Goals

**Goals:**

- 使方向键可靠进入预览，同时保持 iframe 与宿主隔离。
- 让生成指令明确要求 2048 的移动、合并、计分和费用记录的增删、合计、持久化。
- 用固定生成结果和实际模型结果验证完整用户操作，再发布。

**Non-Goals:**

- 不执行模型代码于服务端，不放宽预览沙箱权限。
- 不承诺任意自然语言需求都能一次生成无缺陷应用。

## Decisions

1. **预览焦点由 iframe 自己接收。** 生成或重载后将焦点移入 iframe，并允许用户单击预览重新激活；预览附近显示方向键操作提示。这样键盘事件到达生成脚本，无需把宿主键盘事件转发到不可信代码。避免宿主代理事件，因为它会扩大跨边界协议并可能干扰工作台输入。
2. **指令约束具体状态转换。** 2048 必须在有效方向键操作时压缩并合并每行或每列，每对方块每次移动只合并一次，分数按合并值增加，移动后保存棋盘和分数。费用记录必须在点击添加时读取当下输入、转换为数字、写入记录并重算总额；删除后从状态中移除并保存。相比仅要求“可交互”，这些条件更可测试。
3. **验收以真实操作为准。** 固定结果浏览器测试覆盖焦点、方向键与费用存储桥接；独立真实模型验收在部署地址操作 2048 和费用记录，断言移动、合并得分、20+30=50、删除与刷新恢复。保留现有失败提示和用户主动修复入口，避免模型错误时悄悄展示不可用结果。

## Risks / Trade-offs

- [模型输出仍有随机性] → 真实模型测试明确失败并保留失败样本；针对可复现错误再修正指令或运行环境，不以静态截图代替交互验收。
- [自动聚焦可能影响用户继续输入需求] → 仅在新的预览真正加载时聚焦，工作台输入被用户再次点击后不抢焦点。
- [游戏状态可能仅绘制到 Canvas] → 实际验收以可见数字和分数为优先；若模型选择 Canvas，测试应检查画面变化与可读分数，而非假设固定 DOM 结构。

## Migration Plan

保持现有项目记录与预览存储格式。先运行本地回归和真实模型验收，推送后等待 Vercel 部署 Ready，再在无登录会话逐项复核。若出现回归，可回滚本次提交，已保存项目数据不需迁移。
