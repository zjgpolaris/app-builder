# Design

## Context

工作台把模型返回的 HTML、CSS 和 JavaScript 放入 `sandbox="allow-scripts"` 的 `srcDoc` iframe。该 iframe 使用不透明源，无法直接使用宿主 `localStorage`；这正是现有隔离要求成立的基础。当前 `project.ts` 只保存版本 1 的需求和代码，模型指令还明确禁止生成代码使用存储。参见 `proposal.md` 的动机和 `specs/preview-data-persistence/spec.md` 的行为约束。

## Goals / Non-Goals

**Goals:**

- 保留 iframe 的不透明源和现有 CSP，不给生成代码增加宿主 DOM 或宿主存储访问权限。
- 为生成代码提供常见、同步的 `localStorage` 使用体验，并由宿主异步落盘。
- 让项目修改沿用原数据命名空间，新建项目和两个内置示例使用不同命名空间。
- 兼容已经保存的版本 1 项目；升级后无需重新生成即可继续使用。
- 限制每个预览可写的数据量，损坏或失败时只影响预览数据，不影响项目代码记录。

**Non-Goals:**

- 不提供账户、云端数据库、跨设备同步或多人共享数据。
- 不自动序列化任意 DOM 和 JavaScript 内存状态；生成应用必须明确写入键值存储。
- 不承诺与浏览器 `storage` 事件、多标签页实时同步或完整 Storage 配额行为完全一致。
- 不为历史项目推断或恢复此前从未保存的运行数据。

## Decisions

### 1. 在不透明 iframe 内注入同步 Storage 兼容层

宿主在创建 `srcDoc` 时注入该命名空间已保存的字符串键值快照。预览启动脚本在模型脚本执行前，用内存 Map 实现 `getItem`、`setItem`、`removeItem`、`clear`、`key` 和 `length`，并将其暴露为 `window.localStorage`。每次变更先同步更新预览内存，再通过 `postMessage` 通知宿主持久化。

这样可让普通生成代码继续使用熟悉的同步 API，同时不加入 `allow-same-origin`。相比让模型调用自定义异步 API，它更容易生成正确代码，也能直接覆盖内置示例；相比给 iframe 同源权限，它不会让生成脚本读取工作台存储。

### 2. 宿主只根据消息来源选择命名空间

`Preview` 只接受来自当前 iframe `contentWindow`、`origin === "null"` 且类型匹配的存储消息。消息只能包含操作、键和值，不能指定宿主存储键或项目 ID；宿主使用 React 传入的当前命名空间处理操作。即使生成脚本主动伪造同类型消息，也只能修改自己的预览数据。

持久化记录采用独立前缀，例如 `app-builder:preview-data:<namespace>`，内容为版本化 JSON 字符串映射。解析时只接受普通对象和字符串值。单个命名空间序列化后设置上限，超过上限或 `localStorage` 写入失败时保留 iframe 内当前内存状态，但不更新已落盘记录。

### 3. 项目记录升级为带稳定 ID 的版本 2

新建项目生成稳定随机 ID，修改项目时保留该 ID。最近项目结构升级为版本 2，并继续保存需求、代码和时间。读取版本 1 记录时生成 ID、返回等价版本 2 对象，并尽力写回迁移结果；写回失败仍可在本次会话运行，但不声称迁移已持久化。

生成项目以 ID 作为预览命名空间。待办和记账示例分别使用固定、互不相同的命名空间。新建项目总是生成新 ID，因此不会继承旧项目数据；继续修改沿用 ID，使代码迭代后用户数据仍在。

### 4. 模型与示例显式负责业务状态的保存和恢复

模型指令从“禁止存储”改为：有用户创建或修改的数据时，使用 `localStorage` 保存 JSON，并在启动时进行防御性解析和恢复。内置待办与记账示例采用相同约定，作为无需模型和密钥即可验收的稳定路径。

不采用宿主自动保存 DOM 快照：DOM 快照无法可靠恢复事件监听器、Canvas、派生总额和业务对象，还会保存不应持久化的临时 UI 状态。

### 5. 自动化测试覆盖桥接、安全和交付主路径

浏览器测试使用会读写 `localStorage` 的固定生成结果，验证重新加载预览和刷新页面后数据恢复、新项目数据为空、两个示例互不混用、生成脚本仍无法读取父页面。单元测试覆盖版本 1 项目迁移、损坏预览数据和容量/写入失败。真实模型测试在需求中明确要求持久化，并在页面刷新后验证业务数据，而不仅是代码恢复。

## Risks / Trade-offs

- [模型可能忽略持久化指令] → 由内置示例提供确定性验收，并在真实模型测试中把数据恢复作为失败条件。
- [覆盖 `window.localStorage` 在不同浏览器中可能受属性描述符限制] → 在目标 Chromium 上先以自动化测试验证；若不能覆盖，则在预览脚本执行前用同名词法绑定包装模型脚本作为兼容路径。
- [频繁写入造成主线程开销] → 每次只发送单项操作，宿主限制记录大小；当前 Demo 数据量小，不引入复杂批处理。
- [修改后的代码与旧数据结构不兼容] → 要求生成代码防御性解析；解析失败由应用回退到空业务状态，工作台不修改原记录。
- [旧版本项目迁移写回失败导致 ID 下次变化] → 明确显示项目保存状态；浏览器存储不可用时按规格降级，不承诺跨刷新恢复。

## Migration Plan

1. 先加入项目版本 2、预览数据读写模块及其单元测试，保留版本 1 读取兼容。
2. 接入 iframe Storage 兼容层和宿主消息处理，用固定应用完成安全与恢复测试。
3. 更新示例、模型指令、端到端测试和 README，执行单元测试、浏览器测试、真实生产验收与构建。
4. 部署后用无痕窗口确认免登录生成，再在普通窗口验证重新加载预览和刷新页面后的数据恢复。

若上线后发现预览启动异常，可回退前端版本；项目版本 2 仍包含原有字段，回退代码无法读取时只影响最近项目恢复，不涉及服务端数据迁移。实施时应在部署前保留兼容读取或用快速前滚修复，避免依赖破坏性回滚。
